# Doctrine (Symfony)

## The unit of work
- `persist()` only schedules; `flush()` writes. **One `flush()` per request**, at the end of the use case — a `flush()` inside a loop is one transaction per iteration.
- Doctrine tracks every managed entity: a setter called on a loaded entity is written at flush even without `persist()`. That is dirty checking, and it is also how an accidental mutation reaches the database.
- `clear()` (or `DETACH`) inside a long batch, or the identity map grows until the process dies. Better still: batch with `iterate()`/`toIterable()` and flush every N.

## Loading
- Associations are lazy proxies. Touching one outside the entity manager's lifetime, or after `clear()`, throws — fetch what the caller needs with a `JOIN FETCH` in a DQL query or a query builder.
- `fetch="EAGER"` on the mapping makes every query pay for the association, forever. Decide per query instead.
- `findBy` with an empty criteria array returns the whole table. A filter built from optional request parameters must be validated before it becomes criteria.

## Queries
- DQL operates on entities, not tables: a column name in DQL is a silent error, and `SELECT *` does not exist.
- Parameters are bound (`setParameter`), never concatenated. Identifiers (table, column, direction) cannot be bound — whitelist them.
- For a read-heavy list endpoint, a DQL query with a DTO projection (`SELECT NEW App\Dto\ThingView(...)`) avoids hydrating entities you will only serialise.

## Migrations
- Generated by diff, then **read**. Doctrine's diff renames as drop + add, and it will happily generate a destructive statement.
- The migration is checked in with the entity change, and it is additive against live data. `doctrine:schema:update --force` is not a migration tool — it is `synchronize: true` under another name.

## Tests
- Real engine through Testcontainers or a disposable database, with migrations applied. A mocked `EntityManager` proves the mock — and most Doctrine bugs are about what the database did.
